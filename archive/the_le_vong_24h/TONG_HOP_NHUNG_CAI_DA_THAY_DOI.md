## 2. Các quyết định người dùng đã chốt

Danh sách các quyết định kiến trúc và vận hành đã được người dùng phê duyệt ngày 02/11/2026:

1. **Host chính là Google Cloud Run tại vùng `asia-southeast1` (Singapore):** Triển khai toàn bộ ứng dụng Next.js (SSR + Route Handlers) trên Cloud Run, kết nối gần về mặt địa lý với Supabase Singapore để giảm độ trễ mạng (chốt từ TASK_04, D-64).
2. **Phương án C: Duy trì Vercel (`sin1`) làm bản dự phòng nóng khi demo:** Chuẩn bị sẵn một bản deploy trên Vercel mở sẵn ở Tab 2 trình duyệt máy chiếu. Nếu Cloud Run gặp sự cố mạng hoặc lỗi 5xx quá 2 lần, người thuyết trình chuyển chuột sang Tab 2 trong vòng dưới 5 giây để tiếp tục bài nói (chốt từ TASK_04, D-64).
3. **Chiến lược đóng gói đi giữa và mốc giờ cắt H+15 (03:00 sáng):** Đầu giờ thi triển khai nhanh bằng lệnh `gcloud run deploy --source` (dùng Cloud Buildpacks). Vai A viết Dockerfile multi-stage standalone trên nhánh riêng ở khung giờ H+8–12, thử nghiệm build revision có tag không nhận traffic trước mốc H+12.5. Đến đúng giờ cắt H+15, nếu revision Docker chạy thông thì merge vào `main`; nếu phát sinh lỗi thì hủy nhánh và giữ nguyên Buildpacks để bảo toàn thời gian kiểm thử (chốt từ TASK_04, D-64).
4. **Môi trường Staging S2 kết hợp CSDL mô hình D2:** Staging S2 vận hành dưới dạng một Cloud Run service riêng biệt (`simplifey-staging`, cấu hình `min-instances = 0`, `max-instances = 2`). Sử dụng đúng 2 project Supabase miễn phí (D2): 1 project dev/staging dùng chung cho máy dev và Staging S2; 1 project production dành riêng cho Production và bản dự phòng Vercel (chốt từ TASK_05, D-30).
5. **Kênh AI chính qua Vertex AI (`location: "global"`), AI Studio trả phí dự phòng:** Trên Cloud Run production, ứng dụng gọi mô hình Gemini qua Vertex AI xác thực bằng Service Account nội bộ (`roles/aiplatform.user`), không lưu API key tĩnh trên server. Bản dự phòng Vercel dùng khóa Google AI Studio trả phí thông qua biến phân nhánh `GEMINI_BACKEND` (chốt từ TASK_06, D-66).
6. **Giữ nguyên CSDL Supabase Postgres trên AWS Singapore:** Không chuyển sang Google Cloud SQL để tiết kiệm thời gian thiết lập trong 21 giờ thi. Toàn bộ kết nối server kết nối qua Supavisor Transaction Pooler (cổng 6543, `prepare: false`) bằng biến `DATABASE_URL` (chốt từ TASK_04, D-64, D-65).
7. **Đo lường chi phí hai tầng L1 (Cloud Logging) + L2 (Postgres):** Tầng L1 ghi log JSON cấu trúc qua Pino ra stdout để Cloud Logging tổng hợp biểu đồ thời gian thực. Tầng L2 lưu chi tiết từng lời gọi vào bảng Postgres `ai_usage` (định nghĩa kiểu `AiUsageRow` nội bộ tại `spec/03`, không đưa vào `spec/02` để tránh vượt trần byte) phục vụ hiển thị trên ứng dụng (chốt từ TASK_06, D-66).
8. **Chính sách ngân sách và công tắc bán tự động `AI_DISABLED`:** Thiết lập Google Cloud Budget Alert ngưỡng $20.00 / tháng với 3 mốc cảnh báo 50%, 80%, 100%. Nếu nhận cảnh báo chạm ngưỡng 100%, Vai A chạy lệnh kích hoạt `AI_DISABLED="true"` để ngắt khẩn cấp toàn bộ lời gọi AI trả mã `ERR_AI_UNAVAILABLE`, chuyển ứng dụng sang chế độ an toàn hoặc demo offline (chốt từ TASK_06, D-66).
9. **Tách toàn bộ hạ tầng cloud sang file riêng [`spec/05_HA_TANG_CLOUD.md`](../../spec/05_HA_TANG_CLOUD.md):** Chuyển Mục 18 của `spec/04` sang `spec/05` để giảm dung lượng file `spec/04` từ 41 809 byte (vượt trần 40 000) xuống 35 167 byte ngay sau khi tách (sau TASK_09, TASK_10 là 39 280 byte), bảo đảm trần byte quy chuẩn của dự án (chốt từ TASK_08).
10. **Vai A phụ trách viết Dockerfile ở khung H+8–12:** Vai A nghỉ ngơi và thức dậy lúc H+15 chỉ để đưa ra quyết định merge hoặc bỏ Dockerfile, không viết thêm code lúc rạng sáng (chốt từ TASK_11).
11. **Phê duyệt toàn bộ Lựa chọn A cho các câu hỏi "Cần người quyết" của TASK_04, TASK_05, TASK_06:**
    - TASK_04: Chọn Cloud Run làm host chính, Phương án C dự phòng Vercel, đóng gói đi giữa cắt H+15.
    - TASK_05: Chọn Staging S2 Cloud Run, mô hình D2 hai project Supabase, xác thực WIF (chuẩn bị sẵn key JSON dự phòng).
    - TASK_06: Chọn Vertex AI `global`, đo chi phí L1+L2, tooltip USD trên giao diện Header (giữ sự tập trung sư phạm cho người học, không tạo áp lực tài chính), cơ chế ngắt bán tự động `AI_DISABLED="true"`.

## 3. Thay đổi theo từng quyết định

### 3.1. Sửa D-65 (bộ lọc an toàn, DB driver)
- **Ban đầu thế nào:** Nhánh `docs/d65-sua` (commit `46ae0a5`) do bạn cùng nhóm gửi có nhiều chỗ chưa chuẩn: biểu thức chính quy che secret bị định nghĩa lặp lại ở cả `spec/10` và `spec/04`; hàm `cleanAnswer` chưa quy định thứ tự che; bảng bảo mật ghi RLS chống được SQL Injection; server ghi CSDL thông qua `service-role` key; `ENGINE_VERSION` giữ ở mức 1.5.0; Monaco Editor ghi "tự host nếu..."; thông điệp demo ghi "Che sạch" tạo cam kết quá mức.
- **Vì sao phải đổi:** Đáp ứng Tiêu chí III.3 (xử lý thiên lệch, chống Prompt Injection, lọc nội dung độc hại, che dữ liệu nhạy cảm) và Tiêu chí IV.5 (bảo vệ dữ liệu người dùng). Đồng thời loại bỏ rủi ro bảo mật: dùng `service-role` làm serverless dễ làm cạn kết nối CSDL; Monaco tải CDN dễ bị lỗi nếu mạng phòng thi ngắt kết nối Internet ngoài.
- **Đã đổi gì:**
  - Quy chuẩn vị trí định nghĩa regex secret: Giữ một nơi duy nhất tại ING-110 (`spec/10`), các file khác chỉ trỏ tham chiếu.
  - Sửa regex số điện thoại Việt Nam thành `(?<!\d)(\+84|0)(3|5|7|8|9)[0-9]{8}(?!\d)`.
  - Định nghĩa danh sách `BAD_WORDS` (chuẩn Unicode NFC) và thứ tự che chuẩn hóa: `maskSensitive(redactSecrets(·).code)` (secret biến thành `<REDACTED_SECRET>`, thông tin nhạy cảm PII biến thành `***`).
  - Thêm cấu hình an toàn cho Gemini: `safetySettings` 4 nhóm mức `BLOCK_ONLY_HIGH` trong `callLLMOnce`.
  - Quy định GUARD-07: Mọi vị trí gọi `findForbidden` luôn tự động cộng thêm `BAD_WORDS`, không bị gỡ bởi GUARD-06, áp dụng cho cả `forbidden_external_keywords`.
  - Monaco Editor tự host thông qua `loader.config({ monaco })`, không tải qua CDN, nạp chậm bằng `next/dynamic` với `ssr: false`.
  - Sửa toàn bộ cơ chế ghi CSDL của server: Kết nối qua biến `DATABASE_URL` tới Supavisor Transaction Pooler (cổng 6543, `prepare: false`), không dùng `service-role` cho luồng nghiệp vụ.
  - Nâng hằng số `ENGINE_VERSION` từ `1.5.0` lên `1.6.0`.
  - Thay thế cụm từ "Che sạch" thành "Che các mẫu PII và secret phổ biến", bổ sung 4 ca kiểm thử an toàn D25..D28 trong `spec/50`.

### 3.2. D-64 Hạ tầng Google Cloud Run
- **Ban đầu thế nào:** Hệ thống thiết kế triển khai chính trên Vercel gói free tại Singapore `sin1` (D-27); toàn bộ Next.js chạy trên Vercel Functions; không có cấu hình container Dockerfile; logging xuất stdout để Vercel thu thập; biến môi trường đặt trong Vercel Project Settings; trần file upload zip gắn chặt với giới hạn body của Vercel.
- **Vì sao phải đổi:** Barem chấm điểm chính thức có Tiêu chí VII (10 điểm) yêu cầu triển khai lên Google Cloud hoặc AWS, cấu hình chuẩn production, domain/IP ổn định, bảo mật mạng an toàn. Thiết kế cũ dùng Vercel khiến nhóm nhận 0/10 điểm ở tiêu chí này. Ngoài ra, Vercel Serverless Function gói free có timeout ngắn, dễ bị ngắt kết nối giữa chừng khi phân tích repo lớn.
- **Đã đổi gì:**
  - Chuyển host chính sang Google Cloud Run tại vùng `asia-southeast1` (Singapore), đặt cùng khu vực địa lý với Supabase (`ap-southeast-1`).
  - Cấu hình production cho Cloud Run: 1 vCPU, 2 GiB RAM, `min-instances = 1` (giữ ấm chống cold-start khi demo), `max-instances = 4`, `concurrency = 40`, timeout 300 giây, bật Startup CPU Boost.
  - Thiết kế endpoint kiểm tra sức khỏe `GET /api/health` phục vụ Startup Probe của Cloud Run và Uptime Check của Cloud Monitoring.
  - Bảo mật đám mây: Ingress mở `all` dưới sự bảo vệ DDoS tự động của Google Cloud Edge; tạo Service Account riêng với nguyên tắc đặc quyền tối thiểu; nạp bí mật (`DATABASE_URL`, `GITHUB_TOKEN`) an toàn từ Google Secret Manager.
  - Đóng gói ứng dụng: Thiết kế Dockerfile multi-stage standalone non-root; áp dụng chiến lược đóng gói đi giữa (đầu giờ deploy bằng Buildpacks, viết Dockerfile ở H+8–12, giờ cắt H+15).
  - Vận hành Phương án C: Giữ Vercel `sin1` làm bản dự phòng nóng khi demo, cấu hình Redirect URLs trên Supabase Auth nhận diện cả 2 domain, chuyển tab trình duyệt dưới 5 giây khi có sự cố.

### 3.3. D-30 CI/CD và staging
- **Ban đầu thế nào:** CI/CD dựa vào Vercel Git Integration; quy định chỉ người giữ tài khoản Vercel bấm merge PR vào `main` để deploy; không có môi trường staging độc lập; tài liệu chỉ phân định local dev và production; kiểm tra PR ghi "Không dựa vào bản preview của Vercel" nhưng chỗ khác lại yêu cầu kiểm trên preview.
- **Vì sao phải đổi:** Tiêu chí IV.4 (3 điểm) yêu cầu pipeline CI/CD tự động build, lint, test và tự động trigger deploy staging/production. Thiết kế cũ thiếu hoàn toàn staging, quy trình merge bị nghẽn ở một cá nhân, và vi phạm quy định làm việc nhóm của cuộc thi (yêu cầu cả 5 thành viên đều phải đóng góp commit trên Git).
- **Đã đổi gì:**
  - Viết lại toàn diện quyết định D-30: Xây dựng pipeline tự động hóa bằng GitHub Actions với 3 workflow (`ci.yml`, `security.yml`, `deploy.yml`).
  - Phân định rõ 4 môi trường: Local Dev, Staging S2 (chính), Production, và Vercel Preview S1 (phụ, chỉ xem giao diện tĩnh).
  - Thiết kế môi trường Staging S2 trên Cloud Run: Service `simplifey-staging` (`min-instances = 0`, `max-instances = 2`), kết nối project Supabase dev/staging (mô hình D2).
  - Tự động hóa luồng CD: Khi merge commit vào `main`, pipeline tự động deploy lên Staging S2; sau đó chạy smoke test tự động (probe `GET /api/health` 200 OK và ingest repo demo Q-03 kèm Bearer token bot).
  - Thiết lập cổng kiểm soát an toàn: Sử dụng GitHub Environment `production`, chỉ cho phép Trưởng tích hợp (Vai A) bấm duyệt sau khi xác nhận smoke test trên Staging S2 đạt chuẩn.
  - Xác thực bảo mật: Thiết lập Workload Identity Federation (WIF) giữa GitHub Actions và GCP, phân quyền IAM tối thiểu `roles/run.sourceDeveloper`, chuẩn bị sẵn phương án dự phòng Service Account Key JSON.
  - Bổ sung ca kiểm thử tích hợp `X-09` trong `spec/50` và cập nhật tiêu chuẩn Definition of Done cho pipeline.

### 3.4. D-66 Gemini qua Vertex AI, đo chi phí, ngân sách
- **Ban đầu thế nào:** Gọi Gemini qua Google AI Studio gói Free bằng chuỗi API key tĩnh (`GEMINI_API_KEY`); các con số chi phí USD chỉ là tính toán lý thuyết; chưa có đường ống ghi log đo lường chi phí thời gian thực; chưa có bảng CSDL lưu vết chi phí; chưa thiết lập hạn mức cảnh báo ngân sách trên cloud; tài liệu phỏng đoán sai về mức tiết kiệm 90% từ bộ đệm ẩn (implicit caching).
- **Vì sao phải đổi:** Tiêu chí VI (10 điểm) yêu cầu ứng dụng AI tối ưu hóa ngân sách, cân bằng chi phí - chất lượng - tốc độ, và có giải pháp đo lường cụ thể. Tiêu chí VII.3 yêu cầu bảo mật đám mây an toàn (không để lộ API key). Đồng thời loại bỏ rủi ro bị khóa quota hoặc cạn tiền tài trợ bất ngờ trong 24 giờ thi.
- **Đã đổi gì:**
  - Tích hợp Vertex AI: Chuyển kênh gọi AI chính trên Cloud Run production sang Google Vertex AI (`location: "global"`), xác thực bằng Service Account nội bộ (`roles/aiplatform.user`), dữ liệu người học được Google cam kết không dùng để huấn luyện mô hình.
  - Phân nhánh linh hoạt: Bổ sung biến môi trường `GEMINI_BACKEND` (`"vertex"` cho Cloud Run, `"studio"` cho máy dev và bản dự phòng Vercel dùng gói trả phí). Biến `GEMINI_API_KEY` chỉ bắt buộc khi `GEMINI_BACKEND="studio"`.
  - Thiết kế hệ thống đo lường chi phí hai tầng:
    + Tầng L1 (Cloud Logging): Log JSON qua Pino ra stdout ghi nhận `tokens_in`, `tokens_out`, `cost_usd`, `call_kind`, `retries`, `ai_cache_hit` phục vụ lập biểu đồ giám sát trên Cloud Monitoring.
    + Tầng L2 (Postgres): Tạo bảng CSDL `ai_usage` lưu vết chi phí từng lời gọi AI theo phiên học (định nghĩa kiểu `AiUsageRow` nội bộ tại `spec/03`).
  - Giao diện người dùng: Bổ sung tooltip hover hiển thị chi phí quy đổi `"~{cost} USD (ước tính)"` cạnh bộ đếm token trên thanh Header UI.
  - Chính sách cảnh báo ngân sách: Thiết lập Google Cloud Budget Alert $20.00 / tháng với 3 mốc cảnh báo 50%, 80%, 100%. Bổ sung biến môi trường `AI_DISABLED` và quy trình bán tự động kích hoạt `AI_DISABLED="true"` ngắt khẩn cấp lời gọi AI khi chạm ngưỡng an toàn.
  - Đính chính kỹ thuật: Khẳng định prompt của hệ thống ngắn (~800–2.000 token) chưa đủ ngưỡng kích hoạt implicit cache của Google nên mức tiết kiệm từ cơ chế này hiện là 0%; tính lại chi phí phân tích 1 repo 7 bài là ~0,018 USD (sửa số cũ 0.027 USD); chốt bộ 3 con số cốt lõi bảo vệ trước Ban Giám khảo.

## 8. Việc còn mở và rủi ro

Bảng tổng hợp các vấn đề kỹ thuật còn mở và các rủi ro vận hành cần cả nhóm lưu ý và phối hợp xử lý trước và trong ngày thi:

1. **Khả năng chi trả bằng Credit cuộc thi đối với Vertex AI (chưa kiểm chứng):**
   - *Vấn đề:* Cuộc thi cấp credit Google Cloud cho các đội; tuy nhiên theo tài liệu của Google, một số loại credit dùng thử không chi trả được cho các API trí tuệ nhân tạo (Vertex AI / Gemini API). Nhóm đã đưa nội dung này vào câu hỏi số 4 trong [`CAU_HOI_ANH_CANH.md`](../../CAU_HOI_ANH_CANH.md) để tham vấn mentor.
   - *Biện pháp giảm thiểu:* Vai A chuẩn bị sẵn thẻ thanh toán quốc tế cá nhân (Visa/Mastercard) có số dư sẵn sàng làm nguồn thanh toán dự phòng, đảm bảo dịch vụ Vertex AI không bị ngắt quãng lúc chấm thi.

2. **Dự án Supabase gói Free tự động tạm dừng sau 1 tuần không hoạt động:**
   - *Vấn đề:* Chính sách của Supabase quy định rõ các project gói miễn phí sẽ tự động tạm dừng (pause) nếu không phát sinh truy vấn trong vòng 1 tuần (1 week of inactivity). Nếu xảy ra, ứng dụng sẽ gặp lỗi mất kết nối cơ sở dữ liệu khi chạy thử.
   - *Biện pháp giảm thiểu:* Ngày 06/11/2026 (trước ngày thi 1 ngày), Vai A bắt buộc phải đăng nhập dashboard Supabase kiểm tra trạng thái của cả 2 project (dev/staging và production), bấm unpause nếu bị tạm dừng và chạy thử query ping CSDL qua cổng pooler 6543 để đánh thức kết nối.

3. **Chốt repo demo thật đạt chuẩn theo câu hỏi mở Q-03:**
   - *Vấn đề:* Kịch bản demo và quy trình kiểm thử mốc H+17 dựa vào một repo demo chuẩn. Nếu chọn repo quá lớn hoặc cấu hình phức tạp sẽ gây nghẽn lúc tải và vượt trần token.
   - *Biện pháp giảm thiểu:* Cả nhóm chốt một repo demo công khai trên GitHub viết bằng TypeScript/JavaScript (Express hoặc NestJS), quy mô 20–50 file code, dung lượng nén ≤ 15 MB, có ít nhất một điểm dở kiến trúc rõ ràng để AI phân tích và đưa ra câu hỏi Feynman bám sát dòng code.

4. **Xác thực Workload Identity Federation (WIF) với tài khoản cá nhân:**
   - *Vấn đề:* Thiết lập WIF giữa GitHub Actions và GCP yêu cầu cấu hình OIDC provider chính xác. Nếu cấu hình sai Issuer URL hoặc mapping attribute thì pipeline deploy CI/CD sẽ bị chặn ở bước xác thực.
   - *Biện pháp giảm thiểu:* Thiết lập thử nghiệm WIF trước ngày thi trên repo nháp riêng. Chuẩn bị sẵn phương án dự phòng dùng Service Account Key JSON dán vào GitHub Secret `GCP_SA_KEY` để chuyển đổi tức thì nếu WIF gặp trục trặc trong phòng thi.

5. **Giới hạn Quota đối với repo quy mô lớn 20 node:**
   - *Vấn đề:* Khi phân tích repo lớn 20 node, số lời gọi AI tăng lên (~106 lời gọi ở người đầu tiên) có thể chạm trần Rate Limit (RPM) của mô hình Vertex AI với tài khoản mới.
   - *Biện pháp giảm thiểu:* Thiết lập sẵn tính năng tải chọn lọc một thư mục theo D-63 (`subdir_override`); khuyến cáo Ban Giám khảo demo trên repo mẫu chuẩn bị trước; duy trì `LLM_MAX_RETRIES = 1` và trần token output để không bị nghẽn lệnh.

6. **Dung lượng các file spec đang rất sát trần byte:**
   - *Vấn đề:* Các file [`spec/20`](../../spec/20_AI_GOI_VA_PROMPT.md) (~47.385 / 47.433 byte LF) và [`spec/02`](../../spec/02_CONTRACTS.md) (~44.975 / 45.000 byte LF) đang ở mức cực kỳ sát trần dung lượng quy chuẩn của repo.
   - *Biện pháp giảm thiểu:* Không tự ý thêm các đoạn văn giải thích dài dòng hay tiểu luận vào các file spec này. Mọi kiểu dữ liệu nội bộ chỉ dùng cho 1 file phải được đặt trực tiếp tại file đó (như `AiUsageRow` trong `spec/03`).

7. **Tuân thủ nghiêm ngặt Luật thi của Ban tổ chức (Commit trong giờ thi):**
   - *Vấn đề:* Quy định cuộc thi nêu rõ repo nộp bài thi phải là repo mới tinh lúc bắt đầu, và chỉ những commit được tạo ra trong khung thời gian 21 giờ thi mới được tính điểm hợp lệ. Cấm commit hàng loạt mã nguồn chuẩn bị sẵn từ trước (bulk commit).
   - *Biện pháp giảm thiểu:* Trước giờ thi chỉ thực hiện các cấu hình hạ tầng ngoài repo (tạo Google Cloud project, thiết lập Secret Manager, đánh thức Supabase, cấu hình IAM/WIF, Budget Alert) và thử nghiệm trên repo nháp riêng. Toàn bộ mã nguồn, Dockerfile và các file workflow GitHub Actions (`ci.yml`, `deploy.yml`) bắt buộc phải được các thành viên (cả 5 vai A–E) tự tay commit lần lượt trên repo thi chính thức trong suốt 21 giờ.
